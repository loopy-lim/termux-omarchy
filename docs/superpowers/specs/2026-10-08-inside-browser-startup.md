# Actual browser startup inside Omarchy

The user asks how Chromium can run inside the desktop and authorizes autonomous implementation and physical-device testing. Linux Chromium is a real Ozone Wayland client; Android app inside windows use a separate tablet-owned Shizuku broker. This change makes existing Linux browser startup honest and usable without silently disabling its sandbox or switching Android tasks.

The Android browser menu goes through the same pinned original Omarchy launcher as keyboard shortcuts. Preserve original default-browser choice, literal URL/private argv, existing handoff, focus and original file bytes. Derive only the fresh launch transport from the exact pinned stanza. Run the startup observer in the background with inherited original Wayland/GPU context and fixed null standard streams so original caller URL focus continues immediately. It uses shell=False and adds only the Wayland selection for recognized Chromium commands.

A GTK Wayland window shows preparation, actual failure or a bounded20second unknown-readiness outcome. READY requires a native mapped visible window from the new retained child PID/UID/birth or verified descendant, while the original compositor socket peer/lifetime and fixed action worker remain current. Initial worker admission verifies exact argv and only the selected session/signature/runtime environment against the same process birth before and after; PID alone or a leftover ready file is insufficient. Titles, private URLs, raw stderr and profile data are not logged.

Classify only fixed Chromium startup fatal causes within the first8KiB of own stderr, then continue draining/discarding until child exit. Closing the startup UI or a timeout does not kill the browser or delete its profile. No automatic --no-sandbox, disable-setuid-sandbox, no-zygote, disable-gpu or Android external-task fallback. Existing browser handoff is preserved and never called a newly owned window.

Acceptance: behavioral RED/GREEN for real literal-argv child/fatal/profile preservation, native readiness identity, stale worker/session and caller return/focus before a long-lived child exits; independent source review; exact APK/source receipt; update-only device installation preserving121configuration hashes, KeyBridge/roles/accessibility/microphone denial; actual product GTK error UI on a fresh public offline profile and native inside STOP/START recovery. General sandboxed Chromium web use, physical60/144FPS and every Omarchy/Android app are separate requirements.
