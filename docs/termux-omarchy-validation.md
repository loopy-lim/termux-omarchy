## 입력 설정과 되돌리기

현재 [입력 helper](../termux/omarchy_input.py) `baa10239…`는 다음 10개 preset을 관리한다. `ensure`는 일치하는 프로필을 중복 쓰지 않으며, 원래 9개 원본은 유지하고 추가 설정의 이전 값만 따로 보존한다. 사용자가 바꾼 소유 설정은 덮어쓰지 않는다.

`pauseKeyInterceptingWithEsc=false`는 Escape로 키보드 interception을 중지하지 않는 설정이다. **upstream은 Escape에서 pointer capture를 별도로 해제할 수 있으므로 포인터까지 계속 잡힌다고 보장하지 않는다.** 공개 문자열·Escape 합성 수신은 통과했으나 Meta 조합의 Hypr 반응은 아직 없었고, 물리 키보드/마우스·모든 단축키·배열·IME는 미확인이다.

원본은 `$HOME/.local/share/loopy-omarchy/omarchy-input.json`에 남는다. 기존 i3의 `input.json`은 별도로 보존한다. 기본 Termux 셸에서 현재 helper가 소유한 입력 설정을 되돌리는 명령어는 다음과 같다.

```sh
python "$HOME/.local/share/loopy-omarchy/omarchy_input.py" restore "$(python -c 'import uuid; print(uuid.uuid4())')"
```

복원은 현재 값이 helper가 적용한 값과 같은 알려진 설정만 원본으로 되돌린다. 현재 10개와 옛 9개 snapshot을 모두 지원하고, 관찰된 사용자 변경·관련 없는 설정은 보존한다. 부분 실패면 snapshot을 유지한다. 조회·쓰기는 원자적 CAS가 아니므로 동시에 설정을 편집하지 않는다. secondary-display 별도 저장이 켜져 있으면 거부한다. CLI가 전역 X11 저장소를 사용하므로 프로필 파일 분리가 창별 preference 분리를 의미하지 않는다.

## 권한과 키보드 서비스

[permissions01](../build/diagnostics/termux-omarchy-input-permissions-20261009-01/receipt.json)은 `WRITE_SECURE_SETTINGS` grant와 KeyInterceptor enabled 목록 추가를 기록했고 ROOT의 후속 권한 조회는 `granted=true`였다. [permissions-device02](../build/diagnostics/termux-omarchy-input-permissions-device-20261009-02/receipt.json)는 `ACCESS_RESTRICTED_SETTINGS=allow`를 확인했으며 기존 KeyBridge·Leftcar·Loopy 설정을 보존했다. 그러나 실제 `termuxBound=false`로 실패했다. enabled 목록이나 grant만으로 서비스 실제 연결·모든 키 전달을 주장하지 않는다.

[ZUI rights01](../build/diagnostics/termux-omarchy-zui-rights-device-20261009-01/receipt.json)은 시스템의 auto-run start 거부와 서비스 launch 실패를 기록했다. 앱의 background use는 이미 허용됐지만 ZUI 최초 실행의 Internet/Privacy Policy 동의가 남아 **사용자 승인 대기**다. agent는 동의하지 않았다. 기존 실패 로그는 원인 관찰이며 동의 후 연결 성공은 아직 시험하지 않았다.

사용자의 키보드·CLI 권한 질문에 대한 [실기기 재조회 rights-current10](../build/diagnostics/termux-omarchy-rights-current-device-20261009-10/receipt.json)에서도 `WRITE_SECURE_SETTINGS` grant, 제한된 설정 allow, Termux:X11 입력 서비스 enabled, Termux overlay allow는 유지됐다. 실제 Termux:X11 서비스는 `bound=false`이고 기존 Loopy 입력 우선권·Deskweft 두 서비스만 bound다. 이 조회는 권한을 변경하지 않았으며 물리 키 전달이나 Android root 권한을 증명하지 않는다. 동의 요청은 아직 답변 대기다.

현재 helper의 자동 실행 preference는 upstream 서비스 시작 경로를 켜지만 Android permission grant를 직접 수행하지 않는다. 입력 복원도 permission·enabled 서비스 목록 자체를 복원하는 명령은 아니다. CLI 실행 파일은 Termux private 디렉터리의 앱 UID 권한으로 사용하고 guest는 `omarchy` 사용자다. guest root를 포함한 PRoot의 UID 표시는 Android root 권한을 제공하지 않는다. 재부팅 뒤 권한·서비스 연결 지속성은 별도 미검증이다.

최신 권한 조회는 OEM 개인정보 동의를 다시 승인하거나 화면을 열지 않았다. Termux:X11 preference에 `privacyConsentReceived`라는 키가 없어 [rights-current06](../build/diagnostics/termux-omarchy-rights-current-device-20261009-06/receipt.json)의 해당 값은 `null`이다. 이 키의 부재를 OEM 동의 거부/완료의 증거로 사용하지 않는다. OEM 첫 실행 동의가 필요하다는 근거는 위 ZUI 화면·시스템 거부 기록이며 사용자 승인 요청은 계속 대기 중이다. CLI 실행 성공과 접근성 서비스 연결은 독립적으로 판정한다.

[rights-current07](../build/diagnostics/termux-omarchy-rights-current-device-20261009-07/receipt.json)과 새 Linux 세션 시작 뒤 [rights-current08](../build/diagnostics/termux-omarchy-rights-current-device-20261009-08/receipt.json)은 grant/제한 설정 allow/서비스 enabled/Termux overlay allow를 다시 확인했다. 전체 Bound services에는 기존 Loopy 입력 우선권과 Deskweft만 있었고 Termux:X11은 연결되지 않았다. 이 조회는 permission 쓰기나 OEM 약관 수락을 하지 않았다. Android의 [키 이벤트 필터 API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo#FLAG_REQUEST_FILTER_KEY_EVENTS)는 서비스 간 필터 우선권 제한을 명시한다. 기존 서비스의 실제 충돌은 이 조회로 확인한 것이 아니며, Termux 연결 후 물리 Alt+Tab·Esc 및 KeyBridge 전달을 함께 검사해야 한다. 기존 서비스를 임의로 끄지 않았다.

## 개인 zsh·tmux·KeyBridge 설정과 종료 오류

[keybridge-current01](../build/diagnostics/termux-omarchy-keybridge-current-device-20261009-01/receipt.json)은 현재 Deskweft 설정 화면의 TOML을 읽어 SHA `628cc873…`와 Caps+H/J/K/L, Caps 숫자/F 키, Caps+D/F→F13/F14, Caps 탭 언어 전환을 확인했다. 기존 설정은 수정하지 않았다. 개인 Linux 설정은 [별도 사용 문서](termux-omarchy-personal-profile.md)에 정리했다. Mac의 Git alias·Ctrl+A tmux prefix·Alt 숫자 이동과 선택 도구 연결을 Linux 경로로 이관했으며, 개인 환경변수/인증 정보/셸 기록은 복사하지 않았다. 선택 도구가 없으면 그 초기화를 건너뛴다. Powerlevel10k 전체 모양과 미설치 개발 도구는 이관 완료로 표시하지 않는다.

[personal-install02](../build/diagnostics/termux-omarchy-personal-install-device-20261009-02/receipt.json)은 Foot·Hypr 설정을 백업하고 개인 source include를 적용했다. 원래 `.zshrc`/`.tmux.conf`가 없었기 때문에 새 entry를 만들었다. 기존 XDG `.config/tmux/tmux.conf`가 먼저 선택되는 문제도 해당 파일의 원본을 보존하고 끝에 개인 override를 연결해 해결했다. Hypr reload/config errors 없음·추가 바인딩 4개·기존 작업공간 숫자 바인딩 10개를 확인했다. 물리 Meta/Alt 교환과 Android 시스템 키 전달의 수락은 아니다.

[personal-cli01](../build/diagnostics/termux-omarchy-personal-cli-device-20261009-01/receipt.json)은 Alt 숫자 검사는 통과했으나 XDG 설정 우선순위 때문에 escape-time=10이었다. 후속 [personal-cli02](../build/diagnostics/termux-omarchy-personal-cli-device-20261009-02/receipt.json)는 설정이 적용됐지만 전체 세션이 `resource-replaced`로 종료돼 실패했다. 실제 host tmux를 붙였다 떼는 회귀에서 socket owner 실행 비트 변화를 재현했다. upstream [server_update_socket](https://github.com/tmux/tmux/blob/master/server.c)은 attach 여부에 따라 socket mode를 바꾼다. 이 참고 소스는 현재 main이며 설치한 버전의 동일 commit 증명은 아니다.

당시 resources 수정은 **같은 dev/inode/UID의 Unix socket에서 owner 실행 비트만 변한 경우**를 정상 갱신으로 인정한다. 아래 Yazi DDS의 인증된 재생성 예외 외에 다른 권한·inode·UID·파일 종류나 외부 X server lock/socket 변경은 계속 거부한다. [socket-mode-upgrade01](../build/diagnostics/termux-omarchy-socket-mode-upgrade-device-20261009-01/receipt.json)에 정확한 이전 소스 백업과 새 배포를 기록했다. [personal-cli03](../build/diagnostics/termux-omarchy-personal-cli-device-20261009-03/receipt.json)은 실제 guest tmux의 0600→0700→0600/동일 inode, Alt+1…0으로 1…10 선택, Ctrl+A/secondary prefix 없음/escape-time=0, 전용 tmux 종료와 전체 Linux ready 유지가 통과했다. zsh warm 시작 3회는 59–64ms였으며 물리 입력 지연이 아니다.

[font01](../build/diagnostics/termux-omarchy-personal-font-device-20261009-01/receipt.json)은 창 초기 배치가 안정되기 전 grid를 비교해 실패했다. font02는 영수증을 완성하기 전에 세션이 종료됐고 [별도 관찰](../build/diagnostics/termux-omarchy-personal-font-device-20261009-02/observation.json)을 남겼다. 종료 telemetry는 refresh 단계에서 이미 사라진 PID의 `/proc` 읽기가 `ProcessLookupError`/errno=3을 낸 것으로 기록됐다. native processes 수정은 PID 디렉터리도 사라진 경우에만 이를 종료로 인정한다. 살아 있는 PID 디렉터리의 같은 오류·권한 오류·신원 불일치는 계속 실패시킨다. 경계 double 4개 회귀는 실제 커널 경쟁을 강제로 재현한 증거는 아니다.

[proc-exit-upgrade01](../build/diagnostics/termux-omarchy-proc-exit-upgrade-device-20261009-01/receipt.json)은 정확한 이전 processes source 백업과 새 세션 start를 기록했다. [font03](../build/diagnostics/termux-omarchy-personal-font-device-20261009-03/receipt.json)은 실제 Wayland Foot 창 크기 875×600을 유지하며 Alt+- 뒤 113×35→123×36 grid, Alt++ 뒤 113×35 복원을 확인했다. Alt+0도 터미널까지 전달돼 tmux의 창 10 선택과 충돌하지 않는다. 이 검사는 Hypr IPC로 자기 공개 시험 창에 키를 보내며 Android/물리 키보드 경로를 검증하지 않는다.

[proc-exit-accept01](../build/diagnostics/termux-omarchy-proc-exit-accept-device-20261009-01/receipt.json)은 실제 소유 Foot 아래 자식 프로세스 192개(새 자식 최대 8개)를 2.398초에 생성·종료하고 같은 compositor·오디오·설정 서비스가 유지됨을 확인했다. 공개 시험 창 종료/빈 desktop 확인 뒤 첫 stop 0.353초·자원 정리, fresh start 2.121초·새 token `f136134c…`가 통과했다. 이는 짧은 표본이며 장시간 안정성·모든 프로세스 종료 경쟁의 해소를 입증하지 않는다. 이전 원인 미확인 세션의 종료 이유도 이 새 오류로 소급 단정하지 않는다.

[personal-current02](../build/diagnostics/termux-omarchy-personal-current-device-20261009-02/receipt.json)은 이 새 세션에서 native/개인 source·Foot/Hypr/tmux config SHA와 entry include를 재확인했다. 실제 앱 UID 10323의 GPU node 읽기/쓰기 접근, guest zsh/Git alias·ripgrep·Android 설정 ping과 Quickshell ping이 통과했고 오디오·설정 서비스가 준비된 상태를 유지했다. [current01](../build/diagnostics/termux-omarchy-personal-current-device-20261009-01/receipt.json)은 검사 코드가 설정 ping의 정상 `ready` 응답을 `ok`로 기대해 실패한 기록이다. API 기대값만 고친 current02에서 재검사했으며 runtime 수정·재시작은 하지 않았다.

[tools-current01](../build/diagnostics/termux-omarchy-tools-current-device-20261009-01/receipt.json)은 실제 앱 컨텍스트에서 native/개인 source·config SHA, TUI 런처 `2328d269…`, 585개 설치 목록 SHA, Quickshell ping·GPU 접근·같은 token/오디오/Android 설정 ready를 재확인했다. [Wayland 기본 ANGLE/Vulkan 관찰](../build/diagnostics/termux-omarchy-chromium-wayland-device-20261009-03/receipt.json)은 `xwayland=false` 창과 Adreno renderer를 확인했지만 GPU compositing이 `disabled_software`였다. [Wayland ANGLE/EGL 시험](../build/diagnostics/termux-omarchy-chromium-egl-device-20261009-01/receipt.json)도 공개 DOM 입력은 통과했으나 GPU 프로세스가 3회 종료되고 WebGL을 사용할 수 없었다. 두 후보를 일상 사용 설정에 적용하지 않았다. upstream [Wayland surface factory](https://github.com/chromium/chromium/blob/main/ui/ozone/platform/wayland/gpu/wayland_surface_factory.cc)는 Vulkan 출력의 해당 제한을 기록한다. 이는 현재 움직이는 `main` 소스 참고이며 설치한 Chromium과 동일 소스 해시라는 뜻은 아니다.

현재 통과한 Chromium은 bundle의 기존 XWayland/ANGLE Vulkan 설정이다. 실제 Hypr IPC peer·브라우저 PID birth/소유 supervisor 계보·새 프로필의 DevTools endpoint를 확인하고 공개 페이지 하나를 검사했다. 최초 관찰은 Chromium 앱 모드의 창 class를 잘못 예상해 `not-mapped`를 기록했다. 원본 실패 영수증은 유지하며 후속 검사로 창 표시를 확인했다. XWayland 최초 검사의 창 종료 판정도 class 필터 때문에 신뢰하지 않고 xwayland02의 실제 browser PID 기준 종료 확인을 사용한다. 실제 첫 창 표시 시간·물리 입력·브라우저 지속 FPS·Notion 로그인·sandbox 검증은 이 결과에 포함되지 않는다.

현재 runtime은 foreground native PulseAudio의 `module-aaudio-sink`를 자기 supervisor 아래 실행한다. 전용 0700 runtime과 0600/256-byte 임의 cookie, Unix socket만 사용하고 peer PID·UID·birth를 검증한다. 기존 전역 PulseAudio daemon을 채택하거나 TCP server를 열지 않는다. guest의 `PULSE_SERVER`/`PULSE_COOKIE`와 기존 Hyprland·Chromium wrapper의 옛 TCP 주소를 같은 전용 Unix 경로로 연결했다. 물리 마이크 모듈은 로드하지 않았다.

`/usr/local/bin/omarchy-proot-audio status`는 Omarchy QML이 요구하는 `<volume percent> <mute 0/1> <available 0/1>` 형식이다. `volume 0…100`·`mute-toggle`은 고정 sink를 조작하고 실제 결과를 재조회한다. 실제 메뉴의 OUTPUT 100%와 slider를 한 번 확인한 임시 화면은 `/tmp/loopy-omarchy-audio-panel-20261009-01.png`다. 이 화면과 무음 샘플 성공은 실제 소리가 들렸다는 사용자 확인·Bluetooth/USB 출력 전환·마이크·브라우저 오디오의 수락 증거가 아니다.

오디오만 종료해도 그래픽 세션은 유지됐다. 최초 전체 종료의 `cleanup-operation-failed`/`cleanup-unconfirmed`는 자식이 exec하는 순간 명령줄이 바뀌어 stale record에 대한 signal을 거부한 것이었다. 현재 native `terminate`는 **command-only 변화에만** 다음 반복에서 소유 관계를 새로 확인한다. 바뀐 옛 record에는 signal을 보내지 않고 PID·PGID·UID·birth 변경과 읽기 실패는 계속 거부한다. 동일 UID의 무관한 프로세스와 PID birth 교체를 보존하는 회귀도 통과했다. 실제 같은 오디오 장애 시나리오의 첫 stop/start가 세 번 연속 통과했으며 원본 실패 영수증은 보존한다.

오디오 startup은 exec 직후 Android `/proc`의 빈 cmdline을 journal에 저장하지 않고, 같은 PID·PGID·UID·birth·parent와 예상 argv를 확인한 뒤 기록한다. 다른 executable과 birth 교체를 허용하는 기능이 아니다. 이 수정 전 실제 malformed journal은 일반적인 자동 복구 경로로 채택하지 않았고, 해당 UUID의 정확한 owner와 종료 완료 단계·PID 부재를 확인한 일회성 백업/수정으로 복구했다.

`ready`는 compositor/core 준비 상태다. Quickshell cold start는 별도로 `shell ping`/실제 panel summon을 확인한다. 반복 시험에서 shell 준비 전의 일시적 `not running` 한 번을 관찰했고 같은 살아 있는 compositor에서 기다린 뒤 panel 응답을 확인했다. 이 때문에 세션을 다시 만들지 않았다. 오디오 자동 재시작은 아직 구현하지 않았다. Wi-Fi·Bluetooth 메뉴의 Android 설정 열기/복귀는 아래 범위에서 통과했다. 전체 클립보드·원격 사용은 네트워크 DNS/HTTPS 성공과 별개로 남아 있다.


## 파일 관리자 재실행과 공백 경로

[launch-preflight01](../build/diagnostics/termux-omarchy-app-launch-preflight-device-20261009-01/receipt.json)은 실제 guest의 기존 런처 바이트를 확인했다. TUI focus 런처는 `$@`를 한 문자열로 합쳤고 generic focus 런처는 그 문자열을 다시 unquoted `eval`에 전달했다. [focus-red01](../build/diagnostics/termux-omarchy-tui-focus-red-20261009-01/receipt.json)에서 공백 경로·빈 인수·셸 문자 보존 3개가 실패했다. TUI에 Bash `%q`를 적용한 뒤에도 [partial-red01](../build/diagnostics/termux-omarchy-tui-focus-partial-red-20261009-01/receipt.json)에서 ANSI 인수의 wildcard가 중간 단계에서 펼쳐졌다. 두 번째 문자열 전달도 quote한 [generic source](../termux/omarchy-launch-or-focus)와 [TUI focus source](../termux/omarchy-launch-or-focus-tui)에서 [실제 Bash/exec 11개](../build/diagnostics/termux-omarchy-tui-focus-green-20261009-01/receipt.json)가 통과했다. 기존 창을 focus하는 동작은 유지한다.

[최초 native 경로 검사](../build/diagnostics/termux-omarchy-yazi-spaces-red-device-20261009-01/receipt.json)는 시험용 별도 app-id의 terminal tag 조건에서 먼저 실패했으므로 올바른 폴더 선택의 RED 증거로 사용하지 않는다. 뒤이어 기존 Linux 세션이 종료됐다. [보존한 원래 실패 상태](../build/diagnostics/termux-omarchy-yazi-failed-recovery-device-20261009-01/failed-state.json)의 `operationEvidence.stage=resources`와 조사에서 유일하게 교체된 `yazi+1000/.dds.sock` inode를 확인했다. [설치 버전 Yazi의 공식 stream 소스](https://github.com/sxyazi/yazi/blob/v26.9.1/yazi-dds/src/stream.rs)는 재연결할 때 그 소켓을 제거하고 다시 bind한다. 이 정상 재생성을 일괄 오류로 취급하던 것이 이번 재실행 종료의 원인이다.

현재 resources는 **Yazi DDS 경로의 같은 dev/UID/mode, 새 inode, 실제 Unix peer PID/UID와 현재 소유 프로세스 신원이 모두 확인된 경우**에만 새 소켓을 기록한다. Runtime의 현재 자식 계보를 capture에 전달하며 일반 소켓·핵심 Wayland/X server 자원·symlink 교체는 계속 거부한다. cleanup은 갱신한 정확한 inode만 정리한다. [native RED01](../build/diagnostics/termux-omarchy-yazi-rebind-tests-red-device-20261009-01/receipt.json)은 대체 argv0를 사용한 Python 시험 listener의 시작 실패여서 버그 회귀 증거가 아니다. 표준 Python argv0로 바로잡은 [native RED02](../build/diagnostics/termux-omarchy-yazi-rebind-tests-red-device-20261009-02/receipt.json)에서 기존 API에 새 증거 인수를 무시하는 adapter만 사용해 정상 재생성이 `resource-replaced`로 실패함을 재현했다. [native GREEN01](../build/diagnostics/termux-omarchy-yazi-rebind-tests-green-device-20261009-01/receipt.json)은 adapter 없이 실제 Android 앱 UID의 Unix listener·SO_PEERCRED·/proc 신원 검사 7개를 통과했다. 이 listener fixture와 아래 실제 Yazi GUI 검증을 구분한다.

실패한 세션의 소유 프로세스가 종료됐고 정확한 retained supervisor만 남은 상태를 확인했다. [recovery01](../build/diagnostics/termux-omarchy-yazi-failed-recovery-device-20261009-01/receipt.json)은 연결 거부되는 정확한 시험 소켓을 private 경로에 보존한 뒤 복구 코드가 없는 `Runtime.control` API를 참조해 실패했다. ## SSH와 원격 Wayland 앱

[remote-preflight01](../build/diagnostics/termux-omarchy-remote-preflight-device-20261009-01/receipt.json)은 guest OpenSSH 10.5p1-1·Waypipe 0.11.2-1·Foot 1.27.0-1을 확인했다. rsync·Remmina·FreeRDP는 없다. 기존 Omarchy SSH server helper는 systemctl/UFW를 사용하므로 이 PRoot에서 실행하지 않았다. 새 [원격 CLI](../termux/omarchy-remote)와 [desktop entry](../termux/omarchy-remote.desktop)는 SSH terminal/Wayland app 선택을 제공한다. Gum이 없는 현재 환경에서는 설치된 fzf와 터미널 입력을 사용한다. SSH 설정·인증·서버 키 확인은 OpenSSH에 맡기며 개인 키나 서버 목록을 따로 저장하지 않는다.

Waypipe의 로컬 소켓은 PRoot의 긴 HOME 대신 짧은 `/run/user/1000`에 만들고, 원격 소켓 prefix는 `/tmp`로 별도 지정한다. [Waypipe 0.11.2 설명서](https://manpages.debian.org/unstable/waypipe/waypipe.1.en.html)의 `--remote-socket` 동작을 따른다. GPU 프로토콜은 기본으로 유지하고 `--no-gpu`는 명시적으로 선택한다. GUI에서 입력한 단일 실행 파일 경로는 SSH의 원격 셸을 위해 quote하며, CLI의 SSH 인수는 원래 인수 경계를 유지한다. [quote RED](../build/diagnostics/termux-omarchy-remote-quote-red-20261009-01/receipt.json) 후 [현재 source GREEN 15개](../build/diagnostics/termux-omarchy-remote-quote-green-20261009-01/receipt.json)가 통과했다. 실제 Bash/PTY/셸 경계 검사이며 SSH·Waypipe·선택 도구 recorder만으로 실제 원격 접속을 증명하지 않는다.

별도 Mac Docker Linux arm64 시험 서버를 loopback에만 열고 새 시험 키·고정 host key 확인·이 시험의 ADB reverse 하나를 사용했다. [server receipt](../build/diagnostics/termux-omarchy-remote-server-20261009-01/server.json)는 고정 Debian base digest와 최초 image ID, OpenSSH server 10.6p1-1·Waypipe 0.11.2-1·Foot 1.28.0-1을 기록한다. 이후 수정은 소유 container 내부에만 적용했다. 첫 [GUI01](../build/diagnostics/termux-omarchy-remote-wayland-device-20261009-01/receipt.json)은 서버 Unix forwarding 거부와 XDG_RUNTIME_DIR 부재로 실패했다. 실제 Unix forwarding 거부를 독립 재현한 뒤 [forward fix](../build/diagnostics/termux-omarchy-remote-server-20261009-01/unix-forward-fixed.json)에서 Unix 전달을 허용하고 TCP remote listen은 `PermitListen none`으로 제한했다. [environment fix](../build/diagnostics/termux-omarchy-remote-server-20261009-01/environment-fixed.json)는 전용 사용자 runtime과 TCP 전달 거부를 확인했다. [GUI02](../build/diagnostics/termux-omarchy-remote-wayland-device-20261009-02/receipt.json)는 원격 Vulkan loader 부재로 실패해 [서명된 Debian 패키지 설치](../build/diagnostics/termux-omarchy-remote-server-20261009-01/vulkan-server-install.json)로 이 시험 서버에만 Vulkan/Mesa를 추가했다. 기존 서버나 Android 권한은 바꾸지 않았다.

[GUI03](../build/diagnostics/termux-omarchy-remote-wayland-device-20261009-03/receipt.json)은 실제 창이 표시됐으나 Waypipe proxy 자식의 argv에서 SSH config 경로를 기대한 검사 오류로 실패했다. [existing-window01](../build/diagnostics/termux-omarchy-remote-existing-window-device-20261009-01/receipt.json)은 그 창의 정확한 PID/birth, Waypipe 부모와 private socket prefix, 현재 runtime supervisor까지의 소유 계보를 확인하고 공개 입력·정상 종료를 검사했다. [서버 파일 proof04](../build/diagnostics/termux-omarchy-remote-server-20261009-01/remote-input-proof-04.json)에서 실제 원격 파일의 marker가 일치했다. 원래 FAILED 영수증을 성공으로 바꾸지 않는다.

[ready02](../build/diagnostics/termux-omarchy-remote-ready-device-20261009-02/receipt.json)의 현재 CLI SHA는 `e2e9d8639def32a709f4cdf5cf6bbe7f0ca71c777c5d970789d0921870abcd25`다. 이 source의 [GUI04](../build/diagnostics/termux-omarchy-remote-wayland-device-20261009-04/receipt.json)는 새 원격 파일을 사용하는 실제 창 표시·소유 계보·공개 입력·정상 종료와 같은 Linux/audio/settings ready 유지가 통과했다. [독립 서버 파일 proof05](../build/diagnostics/termux-omarchy-remote-server-20261009-01/remote-input-proof-05.json)도 일치했다. 표시 관찰 0.423초는 USB/ADB 시험 경로의 창 표시 시간이며 인터넷 지연·물리 입력·144 FPS 측정값이 아니다. `--no-gpu`를 강제하지 않았지만 CPU 시험 서버의 GPU 하드웨어 가속을 증명하지는 않는다. Foot의 UTF-8 locale/icon 경고와 Waypipe의 0 크기 damage rectangle 메시지는 보존했으며 전체 프로토콜에 오류가 없다고 표시하지 않는다.

[picker01](../build/diagnostics/termux-omarchy-remote-picker-device-20261009-01/receipt.json)은 등록한 실제 desktop entry를 `gio launch`로 열어 Foot와 실제 fzf 자식 준비·Escape 취소·자기 창만 종료를 확인했다. 0.176초 표시 관찰과 같은 Linux ready가 유지됐다. 실제 사용자의 서버 선택·로그인 흐름은 아직 검사하지 않았다. [device cleanup](../build/diagnostics/termux-omarchy-remote-cleanup-device-20261009-01/receipt.json)과 [host cleanup](../build/diagnostics/termux-omarchy-remote-server-20261009-01/cleanup.json)은 시험 프로세스 종료, 시험용 private key 두 복사본·소유 container/image tag·이 시험의 ADB reverse 제거와 다른 연결 보존을 확인했다. 개인 SSH config/키를 변경하지 않았다. 정리 후 rights-current13에서도 grant/allow/enabled 유지와 Termux bound=false를 재확인했다. 현재 설치된 원격 helper와 desktop entry는 유지하며, 이 배포를 새 기기용 전체 installer의 검증으로 확대하지 않는다.

## Android 설정 연동의 범위

[공용 client](../termux/omarchy_android_client.py)와 [native 서비스](../termux/omarchy_android.py)는 현재 소유 supervisor의 자식이다. 전용 0700 `android/` 아래 새 0600/32-byte cookie·session lease와 Unix socket을 만들고 native peer PID/UID·부모 birth/명령·session marker를 검사한다. guest의 fake UID 1000은 커널 UID 10323과 구분하며, 실제 PRoot CLI ping도 통과했다. HMAC은 session/token/nonce/action을 함께 인증하고 최근 4096개의 nonce만 보관한다. 무제한 replay 방지를 주장하지 않으며, 다른 앱 전체를 통제하는 서비스도 아니다.

`omarchy-proot-settings wifi`, `bluetooth`, `desktop`, `ping`만 허용한다. Wi-Fi는 Android의 [Settings.Panel.ACTION_WIFI](https://developer.android.com/reference/android/provider/Settings.Panel#ACTION_WIFI), Bluetooth는 [Settings.ACTION_BLUETOOTH_SETTINGS](https://developer.android.com/reference/android/provider/Settings#ACTION_BLUETOOTH_SETTINGS)를 호출한다. 임의 shell·package·URL·permission grant/약관 수락을 받지 않는다. TermuxAm의 exit 0/Starting 출력은 실제 화면 전환을 증명하지 않아 응답을 `accepted/android-launch-requested`로 제한한다. 실제 foreground와 정적인 UI 제목은 별도 관찰 영수증으로 확인했다. Wi-Fi SSID·Bluetooth 장치명은 보고서에 수집하지 않았다.

[QML 구성요소](../termux/AndroidSettings.qml)와 [고정 버전 UI patch](../termux/omarchy-settings.patch)는 기존 Omarchy 메뉴의 Android 설정 호출과 실패/재시도 표시를 연결한다. PRoot에서 가짜 Ethernet/NetworkManager/DNS 변경 UI를 표시하지 않는다. 설정 서비스만 종료하는 실제 장애 시험도 Linux/오디오를 유지했고, 전체 정상 종료 뒤 새 cookie/session으로 복구됐다. 서비스 자동 재시작은 구현하지 않았다. 설정 자체의 Wi-Fi 연결 변경·Bluetooth pairing·실제 장치 분리/재연결은 수행하지 않았다. Linux 세션 복귀 경로는 시험했지만 Android의 뒤로 가기 제스처/물리 Esc가 설정 패널을 닫는 동작은 별도 미검증이다.

Termux의 overlay allow는 설정에서 Linux로 돌아올 때의 background activity 호출을 위해 적용했고 [원래 op와 복원 명령](../build/diagnostics/termux-omarchy-overlay-right-device-20261009-01/receipt.json)을 남겼다. 기존 다른 앱의 permission/service 목록을 이 연동에서 바꾸지 않았다. Android는 [background activity 제한](https://developer.android.com/guide/components/activities/secure-bal)을 적용하므로 권한 값·명령 acknowledgement·실제 foreground를 따로 확인한다. CLI가 sudo를 제공해도 Android root 권한을 얻는 것은 아니다.

## 아직 수락하지 않은 항목

물리 키보드/마우스·드래그·단축키·한글 IME, 하드웨어 재부팅, 전체 앱·실제 가청 오디오·클립보드·서비스 통합, 장시간 안정성과 입력 지연은 남아 있다. 아래 동의 전 bound=false 기록은 당시의 실패 증거이며, 사용자 허용 후 실제 연결 결과는 다음 절에 있다. bundle의 Linux Chromium wrapper는 sandbox-off 설정이 있어 sandbox가 검증된 브라우저로 표시하지 않는다. 실행·복원 명령은 [설치 문서](termux-omarchy-installation.md)에 정리했다.

사용자의 키보드·CLI 권한 질문을 [rights-current18](../build/diagnostics/termux-omarchy-rights-current-device-20261009-18/receipt.json)에서 다시 확인했다. `WRITE_SECURE_SETTINGS` grant·제한된 설정 allow·Termux overlay allow·KeyInterceptor enabled는 유지됐으나, **실제 KeyInterceptor bound=false**다. Bound services 전체 블록에는 기존 Loopy 입력 우선권과 Deskweft만 있었다. 최초 파서가 줄바꿈과 전체 component 이름을 잘못 처리한 [rights-current17](../build/diagnostics/termux-omarchy-rights-current-device-20261009-17/receipt.json)은 `INVALID_PARSER_RESULT`로 남기고 수락 증거에서 제외했다. 권한 쓰기·OEM 약관 수락은 수행하지 않았다. [rights-cli03](../build/diagnostics/termux-omarchy-rights-cli-device-20261009-03/receipt.json)은 실제 UID 10323에서 GPU node 읽기/쓰기 접근과 guest UID 1000의 zsh·tmux·ripgrep·Android 설정 ping을 모두 통과했다. 같은 `c3fbc7d7…` 세션과 오디오·설정 ready가 유지됐으며 Android root나 물리 키보드 수락은 증명하지 않는다.

## 키보드·CLI 권한의 현재 상태

[rights-current19](../build/diagnostics/termux-omarchy-rights-current-device-20261009-19/receipt.json)은 사용자 동의 전의 조회다. 사용자가 허용 설정을 켠 뒤 [user-enabled01](../build/diagnostics/termux-omarchy-keyboard-user-enabled-20261009-01/receipt.json)에서 **Termux:X11 KeyInterceptor bound=true**와 X11 foreground를 확인했다. 기존 Loopy 입력 우선권·Deskweft의 연결도 유지됐다. 이 조회에서 다른 앱의 허용 설정을 변경하지 않았다. [native-current01](../build/diagnostics/termux-omarchy-keyboard-native-current-20261009-01/receipt.json)은 실제 UID 10323에서 입력 preset 10개, 같은 `c3fbc7d7…` Linux 세션과 오디오·Android 설정 ready를 확인했다. ### 연결돼도 예약 키를 받지 못한 원인

[공개 modifier 관찰](../build/diagnostics/termux-omarchy-shortcut-observed-device-20261009-01/receipt.json)은 실제 시험 창에 Alt·Alt+Space가 도착하고 Meta·Tab은 도착하지 않은 것을 확인했다. 일반 글자는 기록하지 않았다. 기존 Loopy 입력 서비스를 잠시 해제한 [우선권 비교](../build/diagnostics/termux-omarchy-shortcut-priority-device-20261009-01/receipt.json)도 물리 증상을 바꾸지 못해 [원래 서비스 목록을 복원](../build/diagnostics/termux-omarchy-shortcut-priority-device-20261009-01/restored.json)했다. 개인 KeyBridge 설정은 변경하지 않았다.

실제 Android API의 [live flags01](../build/diagnostics/termux-omarchy-shortcut-live-flags-device-20261009-01/receipt.json)과 [X11 전경 재조회02](../build/diagnostics/termux-omarchy-shortcut-live-flags-device-20261009-02/receipt.json)에서 Termux 서비스의 `flags=0`, `requestsKeyFiltering=false`를 확인했다. 설치 APK는 공식 nightly lock과 다른 `1.03.01-6d3c688-27.08.26`, SHA256 `1370cdab…`다. [설치 APK 분석](../build/diagnostics/termux-omarchy-shortcut-installed-apk-20261009-01/receipt.json)의 실제 Manifest에서 MainActivity는 `android:process="com.termux"`, KeyInterceptor는 기본 `com.termux.x11` 프로세스였다. 실제 DEX의 `recheck()`는 MainActivity의 static instance를 조회한다. 이 공유 상태를 서로 다른 프로세스에서 읽는 구조에서는 서비스가 활성 화면을 찾지 못한다. 현재 설치 동작을 다른 nightly의 소스로 대신 설명하지 않는다.

[수정 후보 영수증](../build/diagnostics/termux-omarchy-shortcut-installed-apk-20261009-01/candidate-receipt.json)은 KeyInterceptor에만 같은 `android:process="com.termux"`를 추가했다. Manifest 증가 20 bytes, 나머지 payload 492개·DEX·native GPU 라이브러리 그대로, 기존 Termux 개발 인증서와 같은 서명, Android parser·16KiB native library alignment와 호스트 회귀 4개를 확인했다. [재현 가능한 patch 도구](../tools/termux_x11_process.py)와 실제 설치본 Manifest fixture를 사용했다. 후보 SHA256은 `d0443400bd9475b5e5275897ec88503877f6af01e85a4e0c38d93f6e960a1948`이다. 아직 설치하거나 물리 예약 키 성공으로 수락하지 않았다. 일반 APK 재설치는 공유 Termux 프로세스도 종료할 수 있어 사용자의 작업 저장 답변을 기다린다.

[rights-cli04](../build/diagnostics/termux-omarchy-rights-cli-device-20261009-04/receipt.json)는 실제 앱 UID 10323의 GPU node 읽기/쓰기 접근, guest UID 1000의 zsh·tmux·ripgrep·Android 설정 ping을 모두 통과했다. 같은 Linux 세션과 오디오·설정 ready가 유지됐다. guest root나 sudo는 Android root를 제공하지 않는다.
