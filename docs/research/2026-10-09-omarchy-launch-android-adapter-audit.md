# Original Omarchy launch and Android adapter audit — 2026-10-09

This is a host-source audit of the native Termux → Weston → Wayland/Hyprland → original Omarchy shell path. It does not claim device interaction, audible playback, a visible Android settings activity, or acceptance of the full original interface. No ADB, package installation, private profile/config reads or writes, or scale changes were performed in this audit.

The one implemented change is `termux/omarchy-launch-webapp`: the PRoot branch now selects the same authenticated Unix Pulse server/cookie as the runtime. Its original Chromium arguments and non-PRoot branch are unchanged. Four tests execute the real shell script against harmless process boundaries; they check exact argument preservation, existing profile bytes/mtime, browser failure propagation, the non-PRoot branch, and an exact pinned-source delta. This source has **not been included in a new guest payload or installed on the device**.

Further full-menu service coverage remains beyond this focused adapter change. Original `omarchy-menu.jsonc:38` directly invokes systemd suspend/hibernate, lines 133–137 expose Linux DNS/QR paths, and lines 361–385 include firmware, clock/timezone, trackpad and storage-encryption actions. Capture entries at lines 65–68 include microphone/webcam options. These need individual capability routing and truthful unsupported/failure states. Installing Linux packages does not supply Android kernel service ownership, hardware permissions or equivalent power/firmware operations. The current runtime has `OMARCHY_UNLIMITED_PROCS=1`, so the old optimization that bypasses menu guard evaluation for restricted PRoot must not be assumed active.

## Keep the Android bridge ownership explicit

The APK-owned path is different: `android/src/dev/loopy/desktop/OmarchyShellStartup.java:24` derives shell/menu/network adapters; `android/assets/omarchy-bridge/platform_action.py` writes a session-scoped request under `/run/loopy`; `android/src/dev/loopy/desktop/AndroidApps.java:130` opens Android activities and handles its own application catalog. Those classes do not establish that the native Termux shell has the APK's request directory, Activity owner, or catalog. Extend the existing authenticated native Termux bridge for this runtime instead of copying the APK file-request path into it.
