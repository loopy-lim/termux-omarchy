# Termux 경로의 안전성·완전성·반응성 현황과 다음 단계 (2026-10-19)

이 문서는 2026-10-19 재구성 이후 Termux 경로의 세 품질 축을 코드 근거로 정리하고, 기기 연결 전에 할 수 있는 것과 연결 후에 해야 하는 것을 구분한다. 측정 없는 성능 주장은 하지 않는다.

## 안전성 (경계와 복구)

**지켜진 경계.** 시작 체인의 모든 단계는 소유자·아이노드·해시로 고정돼 있다: 터미널 명령(install.json + 런타임 11개 SHA) → omarchy.py(활동 시작·입력 소유 조정) → 런타임(boot 증명·자원 장부·감시자). 10/19에 추가한 재시도는 이 경계를 약화하지 않는다. 활동 시작 재시도(2회, 2초 간격)는 반환 코드만 보고, 설정 조회 재시도(2회, 1.5초 간격)는 읽기 전용 `list` 질의에만 적용되며 쓰기·확인 질의는 1회 유지다. 상한은 활동 2×7초+2초, 조회 2×7초+1.5초이고 ensure 전체 상한을 40초로 맞췄다.

**알려진 교착과 유일한 복구 경로.** 같은 부팅 안에서 감시자가 Android에 정리되면(며칠 미사용 후 첫 시작의 대표 원인) `previous-cleanup-unconfirmed`·`supervisor-lost-cleanup-unconfirmed`로 start와 stop이 모두 거절된다. omarchy_boot의 설계는 "다른 커널 부팅만이 옛 프로세스 부재를 증명한다"이므로 재부팅이 유일한 설계 내 복구다. 이 절충을 바꾸는 방법은 두 가지이고 둘 다 사용자 결정이 필요하다:

1. `recover` 동사 추가 — 다른 부팅 복구와 동일한 증명(프로세스 대조·장부 대조·아이노드 고정 정리)을 같은 부팅에 적용하고, 증명 실패분은 격리 보존. 재부팅 없는 복구가 가능해지지만, 같은 부팅에서는 250ms 갱신 창의 미기록 자식이 남을 수 있다는 설계 문서의 거부 사유를 명시적으로 수용하게 된다.
2. 현행 유지 — 재부팅 안내만으로 충분하다고 보는 선택. `doctor`의 `recovery` 필드(2026-10-19 추가)가 이 경로를 상태에서 도출해 알려준다.

**완화하지 않기로 한 것.** 상태 파일의 임의 삭제, 거절 코드의 무시, 재시도 상한의 제거는 모두 안전망 해제다. 문서의 코드 표와 `recovery` 필드가 사용자 안내의 완전성을 담당한다.

## 완전성 (빠짐없이 묶이는가)

**확인된 것.** 삭제 잔여 참조 0(전체 스위트 1,156개 중 삭제 귀속 실패 0). 실패 코드 → 복구 표 문서화. 설치 3중 핀(터미널 소스 ↔ 설치기 SOURCE/PREVIOUS ↔ 런타임 해시 테이블)이 현재 소스와 일치.

**남은 빠진 것.**

1. **환경 의존 테스트 132개** — `build/` 수신증이 이 체크아웃에 없어 ERROR로 끝난다. 수신증이 있던 기계에서만 그린이다. 개선안: 수신증 존재를 전제로 하는 스위트에 공통 스킵 선언(수신증 경로를 읽고 없으면 `skipTest`)을 넣어 "환경 실패"를 "명시적 건너뜀"으로 바꾼다. 실패를 숨기는 게 아니라 전제를 선언하는 것이며, 목록은 러너 출력에 남는다.
2. **첫 시작 실패의 실기 원인 미확정** — 냉시작 경합 가설은 재시도로 완화했지만 실기 확인은 기기 연결 후다. 연결 즉시: `status` → 거절 코드 기록 → 재부팅 복구 확인 → 터미널·런타임 업데이트 적용 → 재시작 확인.
3. **같은 부팅 복구 동사의 도입 여부** — 위 안전성 절의 사용자 결정.

## 반응성 (특히 재진입 지연)

**경로별 비용 구조(코드 상한 기준, 실측 아님).**

| 흐름 | 단계와 상한 | 비고 |
| --- | --- | --- |
| 첫 시작(콜드) | 활동 시작 ≤16초 → ensure ≤40초 → 세션 기동 ≤45초 | 10/19 재시도로 냉시작 1회 실패 제거 |
| 재진입(세션 생존) | 활동 시작 + ensure + 런타임 조기 반환 | **매번 입력 조정을 다시 실행** — 아래 유일한 구조적 여지 |
| 세션 내 입력·스크롤 | 10/12 검증: 휠 보정·MAILBOX·rAF p95 (Notion 16.7ms) | [스크롤 검증 문서](validation/2026-10-12-scroll-responsiveness.md) |
| 앱 전환·복귀 | 소유권 감시 250ms 주기 | 완화는 측정 전에는 금지(기존 원칙) |

**재진입 지연의 구조.** `omarchy.py`는 `start`마다 Termux:X11 활동 시작과 입력 소유 조정(ensure)을 실행하고, 런타임은 생존 세션을 발견하면 조기 반환한다. 즉 재진입 비용 = 활동 시작 + ensure 서브프로세스(파이썬 기동 + 설정 조회 2회)이고, 이것이 "빠른 반응성"의 가장 큰 코드상 여지다. 다만 ensure는 매 진입 시 입력 소유를 재증명하는 안전 장치라서, 생략은 안전성과 직접 충돌한다. 절충안 두 가지:

1. **측정 우선** — [재진입 측정 도구](../tools/measure_termux_reentry.py)를 준비했다(2026-10-19): Termux 셸에서 실제 `loopy-omarchy`를 3~30회 벽시계 측정해 receipt로 남긴다. 구간 귀속(am·ensure·런타임)은 런처가 구간 타임스탬프를 내지 않으므로 이 receipt가 아니라 다음 단계다. 측정 결과 ensure가 수백 ms 수준이면 최적화하지 않는다.
2. **측정이 뒷받침되면** — 생존 세션 재진입에서 ensure를 생략하는 조건을 좁게 정의한다: 직전 조정 기록이 세션 토큰과 일치하고 Termux:X11 설정 해시가 변하지 않았을 때만 생략. 상태 파일에 기록되는 것은 소유·설정 증명의 축소가 아니라 재사용일 뿐, 사용자가 Termux:X11 설정을 바꾸면 즉시 재조정된다.

**세션 내 반응성의 다음 측정.** 10/13 후속(주사율 세션 고정, 그래픽 환경 분리, 오디오 유휴)이 기기에 아직 미적용이므로, 연결 후 순서는 [재연결 검증 계획](validation/2026-10-12-scroll-responsiveness.md#2026-10-13-연결-전-후속-수정--아직-기기-미적용)을 따른다: 휠·터치패드 기준선 → 최소 주사율 해제 비교 → 오디오 절전 분리 시험 → 전환·복귀 생존 → 배터리.

## 순서 요약

기기 연결 전(이 저장소에서 가능): 환경 의존 테스트의 명시적 스킵 선언(완전성 1번) — 별도 커밋으로 진행 가능.
기기 연결 후: 거절 코드 기록 → 재부팅 복구 확인 → 업데이트 적용 → 시작 확인 → 재진입 시간 측정(반응성 1번) → 10/13 검증 계획.
사용자 결정: 같은 부팅 `recover` 동사 도입 여부(안전성), 재진입 ensure 생략 조건의 도입 여부(반응성 2번).

2026-10-20: 반응성 1번의 구간 귀속 기반을 런처에 추가했다. `loopy-omarchy start` 성공 출력의 첫 줄이 `{"status":"phases","activityStartMs":…,"ensureMs":…,"totalMs":…}`가 되고 런타임 status JSON은 마지막 줄로 유지된다(측정 도구 호환). 런타임 잔여 구간은 총 벽시계에서 두 구간을 빼서 계산한다. ensure 생략(반응성 2번)은 이 측정이 뒷받침되기 전까지 구현하지 않는다. 2026-10-20 GPU 기본화 패스의 재진입 지연 외 축: mailbox present 기본화·네이티브 브라우저 승격·termux-x11 Thread-1 착수는 [GPU 기본화 계획](plans/2026-10-20-gpu-aggressive-defaults.md)과 [Thread-1 착수 문서](research/2026-10-20-termux-x11-thread1.md)를 따른다.
